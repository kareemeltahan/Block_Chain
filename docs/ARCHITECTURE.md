# Architecture

## Overview

University-Web3 is a blockchain-backed university management system. All
authoritative state lives on-chain in Solidity contracts. A Python layer
provides a typed, validated, access-controlled API over those contracts.

## Contract Deployment Order

Each contract takes earlier contracts' addresses as constructor arguments.
The topological order is fixed:

```
1. AccessRegistry    ← no constructor args
2. Major             ← no constructor args
3. Professor         ← no constructor args
4. Student           ← no constructor args
5. Course            ← constructor(Professor address)
6. Enrollment        ← constructor(Student address, Course address)
7. University        ← constructor(AccessRegistry, Major, Student,
                                   Professor, Course, Enrollment)
```

After step 7, two more setup transactions are needed:

**setUniversity(University address)** — called on Major, Professor, Student,
Course, and Enrollment. This locks each sub-contract so only the University
address (or the original deployer) can call mutating functions. Without this,
anyone knowing a sub-contract's address can bypass University.sol's RBAC.

**grantRole(ADMIN_ROLE, University address)** — called on AccessRegistry.
University.addProfessor internally calls `accessRegistry.grantRole(INSTRUCTOR_ROLE, addr)`.
University.deleteProfessor calls `accessRegistry.revokeRole(INSTRUCTOR_ROLE, addr)`.
Both require `msg.sender` to hold ADMIN_ROLE on AccessRegistry.
`msg.sender` in those calls is the University contract, not the deployer EOA,
so we explicitly grant University that role here. University's own modifiers
still control who triggers these functions from outside.

## Write Operation Data Flow

Example: `ds.enroll("spring2025", 1, "CS101")`

```
UniversityDataSource.enroll("spring2025", 1, "CS101")
  │
  ▼
EnrollmentDataSource.enroll(student_id=1, course_id="CS101", semester="spring2025")
  │  validates: student_id > 0, course_id non-empty, semester non-empty
  ▼
BaseDataSource._tx(contract.functions.enrollStudentInCourse(1, "CS101", "spring2025"))
  │  builds {"from": deployer_address}
  │  calls fn.transact(params) → web3.py signs + submits
  │  waits for receipt, raises RuntimeError if status == 0
  ▼
University.enrollStudentInCourse(1, "CS101", "spring2025")  [on-chain]
  │  [onlyReg] → ac.hasRole(ADMIN, msg.sender) || ac.hasRole(REGISTRAR, msg.sender)
  │  require stu.isActive(1)
  │  require crs.exists("CS101")
  │  require !enr.getEnrollment(key).active  ← prevents duplicate enrollment
  ▼
Enrollment.enrollStudent(1, "CS101", "spring2025")  [on-chain]
  │  [onlyAuth] → msg.sender == university  ← sub-contract guard
  │  creates EnrollmentRecord{..., studentArrayIndex, courseArrayIndex, semesterArrayIndex}
  │  pushes key to studentEnrollmentKeys[1]
  │  pushes key to courseEnrollmentKeys["CS101"]
  │  pushes key to studentSemesterKeys[1]["spring2025"]
  │  if first time in "spring2025": adds to studentSemesters[1]
  ▼
event StudentEnrolled(1, "CS101", "spring2025") emitted
```

## Semester Storage Design

The on-chain semester data structure uses four parallel mappings:

```
studentEnrollmentKeys[studentId]              → bytes32[]
  All enrollment keys for a student (all semesters)

courseEnrollmentKeys[courseId]                → bytes32[]
  All enrollment keys for a course (all semesters)

studentSemesterKeys[studentId][semester]      → bytes32[]
  Enrollment keys for a student in a specific semester

studentSemesters[studentId]                   → string[]
  Ordered list of distinct semesters (insertion order preserved)
```

This supports four access patterns in O(N) where N is the result set:
- All enrollments for a student
- All enrollments in a course
- All courses a student took in a semester  ← new in v2
- All semesters a student has appeared in  ← new in v2

**Enrollment key:**
```solidity
keccak256(abi.encodePacked(studentId, courseId, semester))
```
The semester is part of the key, so `student=1, course="CS101", semester="spring2025"`
and `student=1, course="CS101", semester="spring2026"` are two different records.
This enables retakes.

**Deletion (swap-and-pop):**
Each `EnrollmentRecord` stores three index fields. On unenrollment, all three
arrays update in O(1): the last element is moved to the deleted element's
position, its index fields are updated, then `pop()` removes the last slot.
The v1 bug was that only the array was updated but the displaced element's index
field was NOT updated, causing subsequent deletions to target the wrong slot.

## Config Lifecycle

```
First run:
  settings.load() → file missing → writes DEFAULT_CONFIG → returns it
  provider.get()  → derives deployer_address from private key → saves

Deploy (deploy_all):
  For each ContractType in DEPLOYMENT_ORDER:
    is_deployed(saved_address)?  → yes: skip  → no: deploy
    deploy_one() → build_transaction → sign → send → wait → save address
  _post_deploy():
    setUniversity() on each NEEDS_BINDING contract
    grantRole(ADMIN_ROLE, University) on AccessRegistry

Subsequent runs:
  All addresses present + is_deployed() returns True → skip deploy
  get_or_deploy() returns live Contract instances immediately
```

**Atomic writes:**
Every `settings.set_contract_address()` call reads fresh from disk, updates
the one address, writes to a temp file, then `os.replace()` renames it.
`os.replace()` is atomic on all POSIX systems and Windows Vista+. This means:
- Partial writes are impossible.
- Rapid sequential deploys (one per contract) cannot clobber each other.

**Nonce tracking:**
The deployer script fetches the current nonce once at the start of `deploy_all()`,
then increments a local counter. Without local tracking, rapid successive
`eth_getTransactionCount` calls return the same nonce (previous tx not yet mined),
causing "replacement transaction underpriced" errors.

## Contract Size Management (EIP-170)

EVM limit: **24,576 bytes** per contract.

Without the optimizer, University.sol compiles to ~34,000 bytes — 38% over limit.
With `compile_standard` and `optimizer.runs = 200`, it lands at ~14,000 bytes.

Why `compile_standard` instead of `compile_files`:
> `compile_files(..., optimize=True)` silently ignores the flag on several
> py-solc-x versions (especially on Windows). The optimizer is never applied.
> `compile_standard` passes a raw Standard JSON dict directly to the solc binary,
> which always honours optimizer settings. This is the only cross-platform fix.

Additional size reduction techniques used in University.sol:
- Sub-contracts declared `immutable` (inlined at compile time, not SLOAD).
- Role constants declared `private constant` (eliminated from storage).
- Internal helpers `_dropCourse` and `_dropStudentEnrollments` reused across
  multiple public functions to avoid duplicated bytecode.
- All single-line forwarding functions kept on one line to minimise source size.
